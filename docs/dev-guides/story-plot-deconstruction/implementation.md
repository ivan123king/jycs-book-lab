# 剧情拆解模块指南

本文定义剧情拆解模块的产品目的、页面交互、数据结构和实现边界。剧情拆解与写作手法拆解同属拆解体系，但它们的分析对象、入口和表单颗粒度不同，不能把剧情拆解简单做成选文拆解弹框的复用版本。

## 目的

剧情拆解用于帮助用户分析一段剧情如何被组织出来，例如装逼打脸、危机救场、误会反转、情感爆发、伏笔回收等。

写作手法拆解关注：

```text
一段原文怎么写
```

剧情拆解关注：

```text
一个剧情单元怎么推进
```

剧情拆解的典型问题：

1. 这段剧情的起点、铺垫、冲突、转折、高潮和余波分别是什么。
2. 多条剧情线如何穿插，例如第 1-3 章推进主线，第 8 章补充支线，第 12-15 章回到主线。
3. 爽点、悬念、误会、反转、人物关系变化如何被安排。
4. 这段剧情能沉淀成什么可复用的写作素材。

## 与写作手法拆解的区别

| 模块 | 分析对象 | 常见来源 | 表单颗粒度 | 结果 |
| --- | --- | --- | --- | --- |
| 写作手法拆解 | 原文片段 | 用户选中文字 | 类型、维度、一个看法输入区 | 写作手法拆解卡片 |
| 剧情拆解 | 剧情单元 | 一个或多个章节范围 | 剧情名称、剧情简介、类型、多个维度输入区 | 剧情拆解卡片 |

剧情拆解可以引用章节范围，也可以在后续版本引用具体原文片段；第一阶段先以章节范围为主要来源。

## 页面入口

当前书工作区应提供独立的“剧情拆解”页面。

页面职责：

1. 展示当前书已有剧情拆解卡片。
2. 支持搜索、按剧情类型筛选、按章节范围筛选、按标签筛选。
3. 提供“新建剧情拆解”按钮。
4. 点击剧情拆解卡片时，以弹框打开详情和编辑表单。
5. 从剧情拆解卡片创建或更新小说内素材。

剧情拆解页面不负责：

1. 不展示写作手法拆解卡片列表。
2. 不承担阅读工作台的原文选区拆解入口。
3. 不把剧情拆解保存为普通笔记。
4. 不把模板维度写死到页面组件中。

## 新建剧情拆解弹框

点击“新建剧情拆解”后打开弹框。

推荐结构：

```text
剧情拆解弹框
├── 章节范围输入
├── 章节内容按钮
├── 剧情名称
├── 剧情简介
├── 剧情类型选择
├── 维度工具区：全部展开 / 全部收起 / 添加维度
├── 维度输入列表
└── 取消 / 保存草稿 / 保存
```

### 章节范围输入

第一阶段必须支持非连续章节范围，因为长篇小说经常多线穿插。输入示例：

```text
1-3, 8, 12-15
```

规则：

1. 支持单章，例如 `8`。
2. 支持连续范围，例如 `1-3`。
3. 支持多个范围用中文逗号或英文逗号分隔，例如 `1-3，8，12-15`。
4. 保存前校验章节序号存在、起始序号不大于结束序号、范围没有非法字符。
5. 可以允许范围重叠输入，但保存时应去重并按章节序号升序生成解析结果。
6. 用户输入原始字符串必须保存，便于后续回显。
7. 解析后的章节引用也必须保存，便于来源追溯。

保存结构应同时包含用户输入和解析结果：

```json
{
  "chapterRangeInput": "1-3, 8, 12-15",
  "chapterRefs": [
    {
      "chapterId": "chapter-000001",
      "chapterOrder": 1,
      "chapterTitleSnapshot": "第一章 初入江湖"
    }
  ]
}
```

不要只保存 `1-3, 8, 12-15` 这类字符串。章节拆分、改名或顺序调整后，解析后的 `chapterId` 和标题快照仍能帮助用户追溯。

### 章节内容按钮

用户填写剧情拆解时可能忘记原章节内容。章节范围输入旁必须提供“章节内容”按钮。

交互规则：

1. 点击后打开章节内容弹框或侧弹层。
2. 弹层左侧展示当前解析出的章节目录。
3. 用户点击某章后，按需加载该章正文。
4. 不要在打开剧情拆解弹框时一次性加载全部章节正文。
5. 范围很大时，章节目录应支持搜索和分页。
6. 章节内容弹框只用于辅助阅读，不直接修改章节正文。
7. 查看已有剧情拆解卡片详情时，也必须保留章节内容入口。

### 剧情名称

剧情名称由用户输入，用于卡片标题和搜索。

示例：

```text
第一次装逼打脸
```

剧情名称不能为空。保存草稿时可以允许为空，但列表中应显示“未命名剧情拆解”。

### 剧情简介

剧情名称下方必须提供一个大输入框，用于让用户先简短描述这段剧情，再进入维度拆解。

剧情简介用途：

1. 让用户先用自己的话概括剧情单元。
2. 作为剧情卡片列表摘要。
3. 作为后续沉淀为剧情素材时的初始摘要。

输入规则：

1. 支持多行文本。
2. 支持 Tab 键在当前行或选中行行首插入中文首行缩进。
3. Shift + Tab 移除已有缩进。
4. 保存空内容时不阻断草稿保存，但正式保存时建议提示用户补充。

### 剧情类型和维度

剧情类型和初始维度来自当前书 `storyPlot` 模板，但模板只提供分析提示，不是强制结构。

规则：

1. 新建剧情拆解时，读取当前书 `deconstruction-plan.json` 中 `currentTemplates.storyPlot` 指向的模板。
2. 用户选择剧情类型后，加载该类型下的默认维度。
3. 用户可以在当前剧情拆解中修改维度名称。
4. 用户可以新增维度。
5. 用户可以删除本次拆解中的维度。
6. 修改、增加或删除本次拆解维度，不应自动改写模板文件。
7. 如果用户希望把当前维度组合变成模板，应通过后续明确的“保存为模板”能力完成，第一阶段可以不做。

因此，剧情拆解卡片需要保存创建时的模板快照和本卡片自己的维度内容。

### 维度折叠

剧情维度可能很多，每个维度旁必须提供折叠按钮。

交互规则：

1. 每个维度可单独展开或收起。
2. 顶部提供“全部展开”和“全部收起”。
3. 展开时展示维度名称和完整输入框。
4. 收起时展示维度名称和用户输入内容的一行摘要，后续内容用 `...` 省略。
5. 没有内容的维度收起时展示“未填写”。
6. 折叠状态属于页面交互状态，不作为正式业务数据保存，除非后续有恢复编辑体验的明确需求。

## 查看和编辑剧情拆解卡片

点击剧情拆解卡片时，使用与新建相同的弹框结构展示详情。

详情弹框必须包含：

1. 章节范围输入和解析结果。
2. 章节内容按钮。
3. 剧情名称。
4. 剧情简介。
5. 剧情类型。
6. 维度输入列表。
7. 来源追溯信息。
8. 沉淀为素材入口。

已有卡片打开后允许编辑。编辑时需要保留原始创建时间，更新 `updatedAt`。

## 未保存修改和草稿

剧情拆解是长表单，必须处理用户临时关闭弹框、切换页面或回阅读模块查看内容的情况。

规则：

1. 弹框内任何字段发生变化后，标记为未保存。
2. 用户关闭弹框时，如果有未保存修改，必须提示。
3. 提示选项至少包含：保存草稿、不保存并关闭、取消。
4. 保存草稿后创建或更新 `status = "draft"` 的剧情拆解卡片。
5. 正式保存后写入 `status = "completed"`。
6. 列表页应能展示草稿状态，避免用户误以为拆解已经完成。

## 数据结构

剧情拆解卡片建议保存在当前小说项目目录：

```text
books/{bookId}/
└── deconstructions/
    └── story-plot-cards.json
```

示例：

```json
{
  "version": 1,
  "items": [
    {
      "id": "story-plot-20260824-0001",
      "bookId": "book-20260824-001",
      "analysisKind": "storyPlot",
      "status": "draft",
      "title": "第一次装逼打脸",
      "summary": "主角被当众压制后，用隐藏实力完成反转，并通过围观者反应放大爽点。",
      "chapterRangeInput": "1-3, 8, 12-15",
      "chapterRefs": [
        {
          "chapterId": "chapter-000001",
          "chapterOrder": 1,
          "chapterTitleSnapshot": "第一章 初入江湖"
        }
      ],
      "planTypeId": "faceSlap",
      "planTypeName": "装逼打脸",
      "dimensions": [
        {
          "id": "setup",
          "name": "铺垫",
          "content": "先让对手和围观者持续低估主角。"
        },
        {
          "id": "climax",
          "name": "高潮",
          "content": "主角展示此前隐藏的能力，完成身份和实力反差。"
        }
      ],
      "tagIds": ["tag-face-slap", "tag-crowd-reaction"],
      "materialIds": ["material-20260824-0001"],
      "createdAt": "2026-08-24T10:30:00+08:00",
      "updatedAt": "2026-08-24T10:35:00+08:00"
    }
  ]
}
```

字段原则：

1. `analysisKind` 固定为 `storyPlot`。
2. `status` 区分草稿和正式完成。
3. `title` 保存剧情名称。
4. `summary` 保存剧情简介。
5. `chapterRangeInput` 保存用户输入原文。
6. `chapterRefs` 保存解析后的章节引用和标题快照。
7. `planTypeId`、`planTypeName` 保存创建时选择的剧情类型快照。
8. `dimensions` 保存本卡片自己的维度和每个维度的内容，不依赖模板后续变化。
9. `materialIds` 记录从该剧情拆解沉淀出的小说内素材。

## 与素材库关系

剧情拆解卡片可以沉淀为素材。剧情素材不是写作手法素材的附属类型，它可以独立表达剧情套路、桥段结构和可复用方法。

示例：

```text
素材标题：装逼打脸桥段的四段式推进
素材类型：剧情结构
可复用方法：压制 -> 反差 -> 爆发 -> 围观确认
来源：某书的剧情拆解卡片
```

沉淀为素材时，应把剧情名称、剧情简介、剧情类型、维度内容和来源章节作为素材草稿的初始内容，但用户必须能二次编辑素材标题、摘要、分类和标签。

## 旧数据兼容

第一阶段新增剧情拆解时，应考虑旧项目：

1. 如果旧项目没有 `deconstructions/story-plot-cards.json`，打开剧情拆解页时创建空集合。
2. 如果旧剧情模板只有类型和维度，不影响新建剧情拆解。
3. 如果后续章节拆分影响 `chapterRefs`，应保留旧标题快照，并提示用户重新校验章节范围。
4. SQLite 索引损坏时，剧情拆解列表必须能从 `story-plot-cards.json` 重建。

## 边界

第一阶段不做：

1. AI 自动生成剧情拆解。
2. 自动判断章节属于哪段剧情。
3. 强制剧情拆解必须引用原文选区。
4. 跨书剧情对比图。
5. 复杂人物关系图和剧情结构图。
