# 后端与本地数据开发指南

本文指导 Wails Go 后端、本地存储、数据模型和业务服务开发。

## 后端职责

后端负责稳定业务能力：

1. 本地文件导入
2. 文本读取和编码处理
3. 章节识别
4. 原始文本保存
5. 用户修正文保存
6. 拆解方案管理
7. 拆解卡片管理
8. 素材库管理
9. 分类和标签管理
10. 搜索、筛选和统计
11. 数据备份、导入和导出
12. 根据项目目录中的正式数据构建可重建索引缓存

正式数据必须保存在用户选择的小说项目目录中。小说正文、导入原文、拆解后需要直接阅读的长文本内容保存为 TXT；书籍元数据、拆解类型、拆解维度、拆解模板、分类、标签和用户通过系统增删改产生的结构化数据保存为 JSON。系统全局设置才保存到应用系统数据目录。SQLite 只能作为索引缓存和快捷查询工具，不能作为唯一数据源。

## 核心数据模型

第一阶段至少应围绕以下模型设计：

1. Book：书籍。
2. Chapter：章节。
3. SourceText：原始文本或原文片段。
4. ReadingContent：用户修正后的正文。
5. DeconstructionPlanState：当前拆解方案引用。
6. DeconstructionDimension：拆解维度。
7. DeconstructionTemplate：拆解模板。
8. DeconstructionCard：拆解卡片。
9. Material：素材。
10. Category：分类。
11. Tag：标签。

模型命名可以按实际代码风格调整，但业务概念不能混淆。

## 存储格式边界

TXT 用于保存用户需要直接阅读或外部打开的长文本：

1. 导入的小说原文。
2. 用户修正后的章节正文。
3. 拆解后需要展示为完整文本的分析内容。
4. 可直接阅读的素材正文。

JSON 用于保存系统结构化数据，方便与 Go 结构体做序列化和反序列化：

1. 书籍基础信息。
2. 章节元数据和正文文件路径。
3. 拆解方案、模板、类型、维度和排序。
4. 拆解卡片元数据和长文本文件路径。
5. 素材元数据和长文本文件路径。
6. 分类、标签和多归属关系。
7. 用户通过系统增删改产生的配置型数据。

应用系统数据目录只保存全局应用设置，例如主题颜色、窗口偏好、最近打开项目列表和最近打开小说项目路径。最近打开小说项目路径只用于应用重启后的入口恢复；任何单本小说的正式阅读位置、该书阅读字号偏好和拆书数据都不应保存到应用系统数据目录。

## 关键关系

必须支持：

```text
Book 1 -> N Chapter
Book 1 -> 1 DeconstructionPlanState
DeconstructionPlanState 1 -> N DeconstructionTemplate reference
DeconstructionTemplate 1 -> N DeconstructionDimension
SourceText 1 -> N DeconstructionCard
DeconstructionCard N -> N Tag
Material N -> N Category
Material N -> N Tag
Material -> SourceText
SourceText -> Book / Chapter / position
```

重点：同一段原文可以有多个拆解，不要设计成一对一。

## 章节识别

章节识别应支持常见中文小说格式：

```text
第一章 标题
第1章 标题
第001章 标题
第一回 标题
卷一 标题
Chapter 1 Title
```

识别结果必须允许用户修正：

1. 修改标题
2. 合并章节
3. 拆分章节
4. 调整顺序
5. 编辑正文

第一阶段的目录拆分采用保守模型：从当前章节开头拆出一个新章节并插入到当前章节之前，当前章节保留剩余正文和原 `chapterId`。这样用户可以把未知章节 A+B+C 逐次拆成 A、B、剩余 C。拆分必须写入 `book.json` 和章节 TXT；如果被拆章节已有选文来源或拆解引用，暂不直接拆分，避免破坏来源偏移和可追溯关系。

自动识别不是最终真相，用户确认后的结构才是正式数据。

## 原文与修正文

必须保留：

1. 原始导入文本。
2. 用户修正后的正文。

这样用户编辑正文后仍能追溯导入来源，避免不可恢复修改。

## 拆解方案

拆解方案属于具体书籍。当前书目录中必须保存当前方案引用 `deconstruction-plan.json`，并在 `deconstruction-templates/` 目录中保存可选模板。`deconstruction-plan.json` 不保存模板内容，只保存不同 `analysisKind` 当前引用的模板文件名，例如 `writingTechnique` 和 `storyPlot`。

第一阶段拆解方案只配置：

1. 模板所属分析类型 `analysisKind`。
2. 模板名称。
3. 拆解类型。
4. 类型下的拆解维度。
5. 类型和维度的顺序。

阅读中创建拆解时，用户选择类型和维度，然后填写自己的看法。不要再把方案设计成单行文本、多行文本、单选、多选、数字、评分等字段表单。

## 素材库

素材不是简单笔记。素材必须包含：

1. 用户分析内容。
2. 来源书籍。
3. 来源章节。
4. 来源原文片段。
5. 拆解类型。
6. 分类。
7. 标签。
8. 创建和更新时间。

分类和标签要支持多归属。

## 错误处理

本地产品必须重视可恢复性：

1. 文件读取失败要返回明确原因。
2. 编码识别失败要允许用户选择或重试。
3. 项目数据文件写入失败不能吞掉错误。
4. 导入过程应避免产生半成品数据。
5. 删除重要数据前应保留确认或可恢复机制。
6. 索引缓存损坏时，应允许删除缓存并从正式数据重建。

## API 设计原则

1. API 以业务动作命名，不以页面命名。
2. 输入输出使用明确结构体。
3. 不把前端显示文案写死在后端。
4. 后端返回稳定错误码或错误类型，前端负责展示。
5. 所有写操作都应返回最终保存后的数据或关键 ID。
